Codebase Map — v0.1 Implementation Plan
1. Назначение документа
Этот документ является основным техническим навигатором разработки Codebase Map v0.1.
Продуктовые требования и границы версии определяются документом:
docs/product_baseline_v0.1.md
Если данный implementation plan и product baseline расходятся, product baseline имеет приоритет.
Разработка должна выполняться последовательно по этапам этого документа. Не следует реализовывать функциональность будущих этапов «на всякий случай».
Каждый этап должен:
- давать конкретный проверяемый результат;
- сохранять приложение в рабочем состоянии;
- иметь автоматические тесты там, где это практически возможно;
- проходить существующие regression tests;
- проходить static analysis;
- не добавлять архитектурные абстракции или зависимости без текущей необходимости.
2. Цель v0.1
Создать кроссплатформенное desktop-приложение для:
Windows + macOS + Linux
которое позволяет открыть локальный Dart/Flutter-проект, проанализировать его исходные файлы и получить интерактивную карту файловых зависимостей.
Основной pipeline:
Select project
      ↓
Recognize project
      ↓
Scan source files
      ↓
Parse Dart directives
      ↓
Resolve dependencies
      ↓
Build AnalysisSnapshot
      ↓
Query / filter graph
      ↓
Tree + Dependency Map + Inspector

Критерий завершения v0.1:
Codebase Map должен успешно открыть и визуализировать собственный репозиторий Codebase Map.

6. Базовая domain model
По мере реализации должна сформироваться модель примерно следующего уровня:
ProjectInfo
Информация о проекте:
- root;
- package name;
- Dart/Flutter;
- доступные source scopes.
SourceFile
Представление исходного файла:
- stable ID;
- relative path;
- scope (lib/test);
- generated flag;
- line count;
- read state.
Stable ID файла — нормализованный путь относительно project root:
lib/app/app.dart

Абсолютные пути не должны становиться публичными ID.
Directive
Dart-директива:
- original URI;
- directive type;
- source location;
- conditional branch, если имеется.
Dependency
Связь между файлами:
- source;
- target, если локальная цель определена;
- dependency type;
- resolution status.
Diagnostic
Проблема, обнаруженная во время анализа:
- category;
- file;
- position;
- human-readable description.
AnalysisSnapshot
Неизменяемый результат одного полного анализа:
files
dependencies
diagnostics
graph indexes

Фильтрация UI не должна изменять snapshot. Базовая модель и правила идентификации файлов следуют техническому анализу Codex.    Вставленный текст
7. Основные правила Dart-анализа
AST вместо regex
Dart-код должен анализироваться через AST.
Не использовать регулярные выражения как основной механизм определения Dart directives.
Повреждённый Dart-файл не должен приводить к падению анализа всего проекта.
URI resolution
Поддерживать:
import '../foo.dart';

как relative dependency.
Поддерживать:
import 'package:current_project/foo.dart';

как ссылку на:
lib/foo.dart

Внешние:
import 'dart:io';
import 'package:flutter/material.dart';
import 'package:some_package/foo.dart';

не становятся локальными nodes.
Не существующая локальная цель получает статус:
unresolved

Существующая цель вне анализируемой области должна отличаться от unresolved.
Direct dependencies
Граф представляет прямые файловые зависимости.
export не разворачивается транзитивно.
show/hide не меняют сам факт файловой зависимости.
part
Каноническая связь:
library → part

part of используется для проверки принадлежности и не должен автоматически создавать искусственное обратное ребро.
Conditional imports
Сохраняются все объявленные варианты.
Результат анализа чужого проекта не должен зависеть от ОС, на которой запущен Codebase Map.
Эти правила фиксируют решения, предложенные для AST, URI resolution, part и conditional imports.    Вставленный текст

- выдаёт детерминированно отсортированный результат.

Использовать временные проекты для:

21. Definition of Done для каждого этапа
Этап считается законченным только если:
□ Acceptance criteria выполнены
□ Новая логика покрыта подходящими тестами
□ Старые тесты проходят

22. Правила работы агента
Перед каждой новой задачей агент должен:
1. прочитать этот implementation plan;
2. при необходимости обратиться к product_baseline_v0.1.md;
3. определить текущий этап;
4. изучить существующую реализацию перед изменениями.
Агент не должен автоматически считать старый план точнее реального кода. Если уже реализованный код и документ расходятся, сначала определить причину и сообщить о существенном противоречии.
Не следует:
- переписывать работающие компоненты без необходимости;
- менять публичные контракты соседних этапов без причины;
- добавлять dependencies «на будущее»;
- реализовывать следующий этап вместе с текущим;
- маскировать diagnostics;
- удалять regression tests ради прохождения новой реализации;
- делать platform-specific предположения там, где требуется переносимость.
Если во время реализации обнаружено решение, способное существенно изменить архитектуру или product behavior, сначала остановиться и вынести его на обсуждение.
Мелкие implementation details агент может решать самостоятельно.
